# マイグレーションとデプロイの手順書

DB のスキーマ変更とフロントエンドのデプロイは**必ずセットで動かす**。片方だけ先に本番へ反映すると本番が壊れる。

2026-08-11 に実際に本番を壊した。その記録と、二度と繰り返さないためのルールをまとめる。

---

## 鉄則

> **マイグレーションの本番適用は、対応するコードがマージ・デプロイされた後に行う。**

DB とフロントエンドは「どのテーブルをどう読み書きするか」という契約で結ばれている。片方だけ動かせば必ず壊れる。

### 破壊的な変更は3段階に分ける

RLS を厳しくする、列を消す、ポリシーを削除するなど、**古いコードが動かなくなる変更**は一度にやらない。

```
1. 新しい経路を追加する（RPC を足すなど）
   → この時点では古い経路も生きている。どちらでも動く
2. コードを新しい経路に切り替えてデプロイ
   → 本番が新経路で安定したことを確認
3. 古い経路を塞ぐ（ゆるいポリシーを削除するなど）
```

こうすればどの瞬間も壊れない。**1 と 3 を同時にやると壊れる。**

### 適用前のチェックリスト

- [ ] `npm run db:dry:prod` で対象マイグレーションを確認した（素の `supabase db push` は使わない。`scripts/db.mjs` 参照）
- [ ] このマイグレーションで**古いコードが動かなくなるか**を検討した
- [ ] 動かなくなるなら、対応するコードのPRが**マージ済み**であることを確認した
- [ ] 影響を受けるコードを網羅的に洗った（後述の「影響範囲の洗い方」）

## 2026-08-11 の事故記録

### 何が起きたか

本番の RLS ポリシーが `USING (true)` に書き換えられており、**ログイン不要で全ユーザーのメールアドレスと全チームの招待コードが読める**状態だった。動作確認のために緩めたまま戻し忘れていたもの。

これを修正するマイグレーション（`0016`〜`0019`）を作り、**PRを出す前に本番へ適用した**。しかし対応するフロントエンドの修正はPRのままマージされていなかった。

結果、**本番DBは新ルール・本番コードは旧ルール**という食い違いが生じ、以下が壊れた。

| 機能 | 状態 |
|---|---|
| チーム作成 | 完全に不可能（`teams_insert` ポリシーを削除したため） |
| フレンド一覧・検索 | 名前が出ない・検索0件 |
| チームタブのメンバー一覧 | 自分1人しか出ない |
| 地図のチームメイト | ピンが表示されない |
| 通知の申請者名 | 「不明なユーザー」 |

カレンダー・メッセージ送受信は無事だった（自分の所属行しか読まないため）。

### なぜ起きたか

**「PRを出す前に本番へ適用して検証する」という順序が誤っていた。**

検証したいのは分かるが、本番は共有環境なので、その間ずっと壊れた状態が晒される。検証はローカル（`supabase start`）でやるべきだった。当時 Docker が無く、ローカル検証ができなかったことが遠因になっている。

### 副次的な失敗

**影響範囲の分析を2回間違えた。**

1. 「RLS を厳しくして壊れるのはチームタブのメンバー一覧だけ」と判断したが、`MapTab` を見落としていた。メンバー一覧のパターンだけを探し、`user_teams` の全参照を洗っていなかった
2. `displayName` が空のユーザーを見つけて不具合として起票したが、実際には対策済みで、5ヶ月前の3件が残っていただけだった。**データの作成日を確認していれば防げた**

コードリーディングによる影響分析は、それ単体では信頼できない。**必ず機械的に全参照を洗う。**

## 適用忘れは CI が検知する

`.github/workflows/migration-check.yml` が、main への push と毎日1回、**本番に未適用のマイグレーションが無いか**を確認する（`db push --dry-run` を実行するだけで、適用は一切しない）。未適用があれば CI が失敗する。

これは2026-08 に**3回連続で同じ取りこぼしが起きた**ため入れた。

| | 起きたこと |
|---|---|
| `0021`–`0023` | マージ後に未適用のまま放置。セキュリティ修正が本番で効いていなかった |
| `0024` | マージ後に未適用。本番の .ics 取り込みと個人予定が壊れていた |
| `0025` | マージ後に未適用。未読バッジが本番で機能していなかった |

いずれも `supabase.from(...)` がエラーを throw しないため **Sentry にも上がらず**、偶然気づくまで放置されていた。

**CI が失敗しても自動では直らない。** 通知されるだけなので、下の手順に従って人が適用すること。

## 影響範囲の洗い方

RLS を変更したら、以下を**すべて**確認する。目視で「ここは大丈夫だろう」と判断しない。

### 1. 対象テーブルへの直接アクセスを全部列挙する

```bash
grep -rn "from('対象テーブル')" src/ -A 5
```

`.eq('userId', 自分)` のように**自分の行しか読まない**ものは安全。他人の行を読むもの、`.in(...)` で他人を含むものは要注意。

### 2. `.insert().select()` を探す

```bash
grep -rn -A 4 "\.insert(\|\.upsert(" src/ | grep -B 2 "\.select("
```

`.select()` は `RETURNING` を生成し、**PostgreSQL は RETURNING で返る行にも SELECT ポリシーを適用する**。

チーム作成が壊れたのはこれ。作成の瞬間、作成者はまだ `user_teams` に入っていないため `teams_select` を満たさず、行が返らずに `.single()` が失敗していた。

### 3. ポリシー式が他テーブルを参照していないか

**ポリシー式が別テーブルを参照すると、そのテーブルの RLS も適用される。**

`locations_select` は「相手が自分と同じチームか」を判定するために相手の `user_teams` 行を読む必要があったが、`user_teams` を自分の行のみに絞った結果、判定が成立しなくなった。

対策は `SECURITY DEFINER` のヘルパ関数を経由すること（`shares_team_for_location` / `is_team_member` がその例）。

> **注意**: ポリシー式は問い合わせユーザーの権限で評価されるため、そこから呼ぶ関数は `REVOKE` してはいけない。REVOKE すると SELECT 自体が `permission denied` になる。

### 4. 匿名アクセスで実測する

修正後、匿名で全テーブルを叩いて確認する。読み取りは0件、書き込みは `42501` が期待値。

```bash
set -a; . ./.env.local; set +a
for t in users teams user_teams team_messages events locations user_friends friend_requests team_invitations; do
  curl -s "$VITE_SUPABASE_URL/rest/v1/$t?select=*&limit=50" -H "apikey: $VITE_SUPABASE_ANON_KEY"
done
```

**書き込みの検査は必ず外部キー違反する値を使う。** 実在する値を使うと本番にゴミが作られる。実際に `teams` へ検証用の行を作ってしまい、手で消す羽目になった（`teams` には DELETE ポリシーが無いため匿名では消せない）。

> PostgREST は RLS で0件削除になっても `204` を返す。**削除が成功したように見えるので注意。**

### 5. RPC の存在確認

コードが呼ぶ RPC が本番に存在するか確認する。**引数を正しく渡すこと**。引数なしで叩くと、引数が必要な関数が `PGRST202`（存在しない）と誤判定される。

- `42501` → 存在する（匿名は拒否＝正常）
- `PGRST202` → **本番に存在しない**

## マイグレーション番号のルール

**番号を重複させない。** Supabase の履歴テーブルはバージョン番号を主キーにするため、同じ番号のファイルが2つあると片方しか記録されない。

過去に `0007` と `0008` が重複し、以下が起きた。

- `0007_join_team_by_code.sql` が**本番に適用されないまま「適用済み」と記録**された
- そのため `db push` でも永久にスキップされ、`join_team_by_code` 関数が本番に存在しなかった
- 結果、**招待コードでのチーム参加が機能していなかった**（`events.teamId` は `NOT NULL` なので、カレンダーも実質使えなかった）

一度履歴に記録された番号は再適用されない。**新しい番号で入れ直すしかない**（`0015` がその対応）。

**被害は1件とは限らない。** 重複した番号の数だけ取りこぼしがある。実際 `0008` でも同じことが起きており、`0008_event_timezone.sql` の `events.timezone` 列が本番に存在しないまま長期間放置されていた。

- 症状: 予定の追加・編集が全ユーザーで失敗し `Could not find the 'timezone' column of 'events' in the schema cache` が返る
- 閲覧（`select *`）と削除は列名を指定しないので動くため、**「予定は見えるのに追加も編集もできない」**という分かりにくい壊れ方をする
- ローカルは `db reset` で全ファイルが走るため**再現しない**。本番だけで起きる
- 対応は `0020_restore_event_timezone.sql`

**番号重複を解消したら、重複していた側の中身が本番に入っているかを列・関数レベルで必ず確認すること。** リナンバーしただけでは本番は直らない。関数は上の「5. RPC の存在確認」で、列は本番に対して直接引く。

```sql
-- 期待する列が本当にあるか
select column_name from information_schema.columns
where table_schema = 'public' and table_name = 'events'
order by ordinal_position;

-- 履歴に記録されている番号（ここに載っている番号は二度と再適用されない）
select version from supabase_migrations.schema_migrations order by version;
```

## 参考: 現在の設計

RLS は「自分の行のみ」を基本とし、それ以上が必要な操作は `SECURITY DEFINER` の RPC に集約している。

| やりたいこと | 使うもの |
|---|---|
| 他人の表示名を引く | `get_public_profiles(ids)` |
| ユーザーを探す | `search_users(query)` |
| チームのメンバー一覧 | `list_team_members(team_id)` |
| 同じチームの人を集める | `list_my_teammates()` |
| チームを作る | `create_team(name, policy)` |
| 招待コードで参加 | `join_team_by_code(code)` |

**テーブルの門番（RLS）を、関数の中の門番に置き換えている。** 関数は必要な列しか返さないため、メールアドレス等は外に出ない。

新しく RPC を足すときは:

- `SET search_path = public` を付ける（search_path 注入の防止）
- 関数の冒頭で `auth.uid()` と権限を検証する
- `authenticated` にのみ `GRANT` し、`anon` からは `REVOKE` する
- ただし**ポリシー式から呼ぶ関数は REVOKE しない**（前述）
